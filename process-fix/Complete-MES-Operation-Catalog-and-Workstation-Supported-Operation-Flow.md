# Complete MES Operation Catalog and Workstation-Supported Operation Flow

## Objective

Review the current MES codebase and complete the missing Operation management flow.

The required domain model is:

```text
Operation Catalog
        ↓
Workstation Operation Capability
        ↓
Work Center Composition
        ↓
Routing Operation
        ↓
Work Order Planning and Execution

A Workstation must allow users to configure the Operations that can be executed at that station.

However, an Operation must remain a reusable central master-data definition. Do not create isolated duplicate Operations owned only by individual Workstations.

The current architecture already distinguishes:

MD_OPERATION
= Central reusable Operation definition

MD_WORKSTATION_OPERATION_CAPABILITY
= Operation supported by a specific Workstation, including timing and execution parameters

MD_WORK_CENTER_COMPOSITION
= Operations exposed by Workstations inside a Work Center

MD_ROUTING_OPERATION
= Product-routing step that references an Operation and a logical Work Center

The codebase currently records that Workstation forms persist supported Operation capabilities, while Work Center composition selects Operations exposed by those Workstations. Preserve that architecture.

Routing must continue to reference a central Operation and a logical Work Center, not a Workstation directly.

2. Central Operation Catalog

If complete Operation management does not already exist, add it.

Recommended routes:

/master-data/operations
/master-data/operations/new
/master-data/operations/:id
/master-data/operations/:id/edit

The Operation entity must remain the reusable MES-wide definition.

Required fields:

interface Operation {
  operationId: string;
  operationCode: string;

  name: LocalizedText;
  description?: LocalizedText;

  operationType:
    | "Production"
    | "Inspection"
    | "Packing"
    | "Handling";

  confirmationMode:
    | "StartFinish"
    | "QuantityOnly"
    | "Auto";

  quantityReporting:
    | "GoodOnly"
    | "GoodScrap";

  requiresMaterialScan: boolean;
  requiresOutputLabel: boolean;
  allowPartialCompletion: boolean;

  status: "Active" | "Inactive";

  createdByUserId: string;
  createdAt: string;
  updatedByUserId: string;
  updatedAt: string;
}

The existing domain catalog defines Operation as the standard catalog used by production, inspection, packing, and handling processes. It owns execution behaviour such as confirmation mode, quantity reporting, material scanning, output-label requirements, and partial completion.

6. Clarify Timing Ownership

Do not store a free-floating cycle time directly on Work Center.

Use this ownership model:

Operation
= Reusable process definition

Workstation Operation Capability
= Workstation-specific estimated execution parameters

Production Standard
= Released Product Revision and Routing Operation-specific standard

Work Center
= Logical grouping of Workstations and their supported Operations

Timing resolution:

Released resource-specific Production Standard
→ Released Work Center Production Standard
→ Workstation Operation Capability estimate
→ Missing timing configuration

The Workstation cycle time is a planning estimate. It must not silently override a Released Production Standard.

8. Workstation Operation Validation

Enforce:

At least one Operation for planning-enabled Workstations.
No duplicate active Operation on the same Workstation.
Operation must be active.
cycleTimeSec > 0.
baseQuantity > 0.
setupTimeMin >= 0.
efficiencyFactor > 0 when provided.
Effective end must be later than effective start.
Removing a supported Operation must check Work Center, Routing, planning, and Work Order dependencies.
Do not destructively overwrite historical capability records.
End old capability rows through effective dating when required.

Stable errors:

WORKSTATION_OPERATION_REFERENCED

9. Work Center Composition

A Work Center must be built from Workstations and the Operations supported by those Workstations.

Required flow:

Select Shopfloor
→ Select one or more Workstations
→ Display each Workstation’s supported Operations
→ Select the Operations exposed by the Work Center

Example:

Workstation:
Laser Cutting Station 01
WS-20260725-0004

Supported Operations:

[x] Blank Cutting
    Workstation estimate: 18 sec

[x] Profile Cutting
    Workstation estimate: 32 sec

[ ] Hole Drilling
    Workstation estimate: 25 sec

Rules:

At least one Workstation is required.
Each selected Workstation must contribute at least one selected Operation.
At least one Operation must be exposed by the Work Center.
Only Operations actively supported by the selected Workstation may be selected.
Workstation and Work Center must belong to the same Shopfloor hierarchy.
Removing an Operation must check Routing, readiness, allocation, and Work Order dependencies.
Routing continues to reference Work Center, not Workstation.
10. Routing Operation Flow

Routing creation must use the central Operation catalog.

For each Routing step:

Sequence
Operation
Default Work Center
Predecessors
Scheduling mode
Queue time
Move time
Overlap rules

The selected Work Center must expose the selected Operation through its current Workstation composition.

Validation:

Routing Operation
→ Operation is active
→ Work Center is active
→ Work Center exposes Operation
→ At least one active Workstation supports Operation

Reject invalid combinations with:

WORKCENTER_OPERATION_NOT_SUPPORTED
ROUTING_OPERATION_INACTIVE
ROUTING_WORKCENTER_INVALID

Routing Operations own sequence, dependencies, queue time, move time, and scheduling parameters; they reference the central Operation and default Work Center.

11. Operation Skill Requirements

Operation Skill Requirements must only assign worker skills to an existing Operation or Routing Operation.

They are not an Operation creation flow.

Use this separation:

Operation
= What work is performed

Workstation Operation Capability
= Where and how the Operation can be performed

Operation Skill Requirement
= Which worker qualification is required

Routing Operation
= Where the Operation appears in a product route

Do not allow the Skill Requirement page to create incomplete or hidden Operations.

If the requested Operation is missing, provide a navigation or inline creation action that creates a real central Operation first.

The modal must clearly explain this workflow:

1. Create or reuse an Operation in the central Operation Catalog.
2. Configure the Operation as supported by one or more Workstations.
3. Enter Workstation-specific cycle time and execution estimates.
4. Compose a Work Center from Workstations and their supported Operations.
5. Use the Operation and Work Center together in Routing.
6. Assign worker Skill Requirements to the Routing Operation.
7. Planning resolves Workstation, Machine Group, Machine Units, Calendar, Capability, and Production Standard.
8. Kiosk executes the resulting Work Order Operation at the allocated Workstation.

Also explain:

Operation is not owned by Workstation.
Workstation only declares that it supports the Operation.

And:

Cycle time entered at Workstation is an estimate.
Released Production Standards take precedence during planning.

16. Acceptance Criteria

The task is complete when:

A central Operation Catalog exists with usable CRUD.
Operation codes are backend-generated and read-only.
Workstation create/edit supports one or more Operations.
Workstation Operation capability stores cycle time and related estimates.
Users can create a central Operation inline from the Workstation form.
Inline creation selects the new Operation immediately.
Failed inline creation leaves no ghost option.
Work Center composition selects Workstations and their supported Operations.
A Work Center exposes at least one Operation.
Work Center does not own a free-floating cycle-time field.
Routing references central Operation plus logical Work Center.
Routing rejects Work Centers that do not expose the selected Operation.
Operation Skill Requirements remain separate from Operation creation.
Detail/help modals explain the complete workflow.
No duplicate per-Workstation Operation definitions are created.
Existing Routing, readiness, Production Standard, and Work Order flows remain compatible.
The comprehensive flow script passes.
Console and service logs contain no unexplained errors.
