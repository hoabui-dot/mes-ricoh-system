# Real Printer Only Cleanup and Zebra CUPS Flapping Audit

Date: 2026-07-26
Status: IMPLEMENTED_LOCALLY / ARM64_IMAGE_PUSHED / REMOTE_ADAPTER_RESTART_PENDING

## Finding

`Zebra-GK420t-CUPS` is a real CUPS printer record. Its status is produced by
`CupsPrinterDriver`, which queries the configured CUPS queue through IPP. The
heartbeat publisher persists the probe result and publishes heartbeat/status
events.

The source has a 15-second heartbeat default and the CUPS driver retries three
times with 200 ms delays. Therefore a one-second ONLINE/OFFLINE loop cannot be
generated by the current default heartbeat cadence. The current CUPS probe has
no hysteresis: a transient IPP failure is immediately mapped to `OFFLINE`, and
the next successful probe is immediately mapped to `ONLINE`. A remote adapter
running an older image, a non-default one-second heartbeat configuration, or
multiple adapter instances publishing the same printer code can therefore
produce the reported rapid alternation. The adapter port is not available from
this workspace, so the live remote log/process-count check could not be
performed here.

## Runtime correction

The old mixed simulation/runtime path has been removed from the codebase:

- `VirtualPrinterSimulator` hosted service and API endpoints were removed.
- `SimulationPrinterDriver` was removed.
- Real driver selection now supports `cups` and raw `tcp` only.
- Startup migration deletes simulation records and legacy demo printer codes
  (`Printer-01`, `Printer-02`, `Printer-03`, `printer-01`) before seeding the
  physical `Zebra-GK420t-CUPS` record.
- The database default driver changed from `simulation` to `cups`.
- Device Simulator no longer exposes printer simulation control endpoints or
  receives the printer-adapter simulation connection from Compose.
- Kiosk removed the `Thiết bị mô phỏng` section from the device network view.
- Kiosk removed the simulation-printer panel and no longer requests
  `includeSimulation=true`.
- Projection Service and Kiosk printer-ready APIs no longer expose the
  simulation filter.
- Kiosk dispatch now has only the production-printer target; missing dispatch
  targets in Job Engine events default to `production-printer`.

## Legacy Projection Row Correction

The Kiosk entries `PRINTER-01`, `PRINTER-02`, and `PRINTER-03` survived in the
persisted Projection SQLite database from the previous simulator seed. Old
simulator heartbeat events were also still accepted by the projection consumer.
The Projection Service now removes the known legacy IDs idempotently at startup
and ignores those printer codes, plus printer events marked with a `simulation`
driver. It no longer seeds `printer-01`.

After restart, `GET /api/projection/devices` returned only the real
`Zebra-GK420t-CUPS` printer. Startup logs confirmed old simulator heartbeats
were received and ignored, so a stale adapter cannot recreate those rows.

## Remote Probe Diagnostics

The Printer Adapter now logs adapter ID, process ID, heartbeat interval, cycle
duration, printer count, probe start/end, driver/host/port, previous and
normalized status, elapsed milliseconds, CUPS IPP state/reasons/queued jobs,
retry attempts, TCP fallback, and published events. Credentials are never
logged. The default heartbeat remains 15 seconds with three 200 ms CUPS retries.
The reported 1-2 second loop should now be attributable in remote logs to a
configured interval, duplicate process IDs, or repeated CUPS probe failures.

Local runtime audit found the immediate simulator source: an obsolete
`printer-adapter` container running `printer-adapter:local-rabbitmq-amd64` was
still hosting `VirtualPrinterSimulator` and publishing `Printer-01/02/03`
events. That container was stopped and removed. After one heartbeat interval,
no new simulator events arrived and the Projection API still contained only
`Zebra-GK420t-CUPS`.

## Kiosk Active-Printer 502 Correction

The Kiosk `GET /api/projection/printers/active` route is a Projection Service
proxy to `http://100.68.50.41:5003/api/printers/active`. The 502 was caused by
the adapter container being stopped, not by a missing endpoint. Starting the
new real-printer image restored the route: the adapter reported RabbitMQ
connected and the Kiosk proxy returned HTTP 200 with `[]` when no printer was
activated for production. The standalone compose file now points to the
pushed ARM64 real-printer image with explicit runtime settings.
