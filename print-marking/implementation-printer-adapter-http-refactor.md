# Printer Adapter HTTP Refactor Implementation

Date: 2026-07-26
Status: implemented and runtime verified

## Scope

The duplicated `print-marking/mes-frontend` and `print-marking/mes-platform` trees were removed. The active print-marking system is `print-marking/station-agent`.

The Printer Adapter is now an independently deployable HTTP service. It keeps the existing rendering, printer-driver, CUPS, virtual-printer, queue, audit, and SQLite responsibilities. RabbitMQ command consumption and event publishing were removed from the adapter runtime.

## Runtime flow

```text
Job Engine
  -> POST /api/print
Printer Adapter
  -> render template
  -> enqueue/process ZPL
  -> physical Zebra/CUPS or local simulator
  <- ProductionBatchPrintedEvent
Job Engine
  -> applies the result using PrinterBatchPrintedConsumer
```

The Job Engine still uses RabbitMQ for the rest of the station event topology. Its legacy `printer.batch.printed` consumer remains for compatibility with older producers, but the normal batch-print path is now direct HTTP.

## HTTP contract

- `GET /api/health` returns adapter status, version, uptime, and printer count.
- `POST /api/print` accepts `ProductionBatchPrintCommand` and returns `ProductionBatchPrintedEvent`.
- `GET /api/jobs/{id}` reads local printer-job state.
- Existing printer, template, render, print-history, and maintenance endpoints remain owned by the adapter.

The batch command is the existing unified contract and includes the production order number, printer target, dispatch target, batch size, and label items. No UUIDs are generated by the client and no RabbitMQ envelope is required at the adapter boundary.

## Configuration

Set `PRINTER_ADAPTER_URL` on Job Engine, Kiosk UI, Device Simulator, and Projection Service. The compose default is:

```text
http://100.68.50.41:5003
```

The independent adapter image is built with:

```text
vanhoadotbui2628/printer-adapter:independent-http-20260726
```

Deploy that image separately on port `5003`, with its printer SQLite path, CUPS access, and physical printer configuration. Printer Adapter does not require Redis; the calling service owns caching and idempotency. The Station Agent compose file intentionally does not define a `printer-adapter` service.

## RabbitMQ and Redis decision

The main MES platform compose (`infra/docker-compose.platform.yml`) provides Kafka, Keycloak, Kong, and observability. It does not provide RabbitMQ or Redis. The Station Agent services currently require RabbitMQ and Redis, so its compose stack runs one Station Agent RabbitMQ and Redis pair. This is not a duplicate of an existing MES broker because no such broker exists in the current platform.

The stack supports future reuse through:

- `STATION_RABBITMQ_HOST`
- `STATION_REDIS_CONNECTION_STRING`

If shared brokers are introduced later, set those variables and remove the local broker services only after their external network and health checks are provided.

## Cleanup and compatibility

Removed from the Printer Adapter runtime:

- RabbitMQ batch/job consumer
- RabbitMQ heartbeat publisher
- RabbitMQ printer-health publisher
- RabbitMQ dependency from the Printer Adapter infrastructure project

The virtual printer simulator remains available for local TCP-driver testing, but it no longer publishes RabbitMQ heartbeats. Health is obtained through the adapter HTTP API and printer endpoints.

## Verification

- All three Station Agent compose files pass `docker compose config --quiet`.
- Printer Adapter Docker image builds successfully.
- Job Engine, Kiosk UI, Projection Service, and Device Simulator images build successfully.
- Station Agent runtime starts without a local Printer Adapter service.
- RabbitMQ and Redis containers report healthy.
- Job Engine reports healthy and logs successful RabbitMQ publisher/consumer connections.
- Projection Service reports healthy and starts its event consumers.
- Device Simulator reports healthy.

The initial runtime start exposed an existing bind-mount permission issue for `sqlite-databases`; the directory was made writable for the container application user and the services stabilized without source changes to their database initialization.

No image push was performed. The image is built locally and must be pushed only from a registry-authenticated deployment environment.
